# Release manifests

Vanta's stable updater uses a versioned JSON manifest attached to each GitHub
Release as \`manifest.json\`.

## Stable endpoint

The updater retrieves:

\`https://github.com/ItsDropper/Vanta/releases/latest/download/manifest.json\`

The manifest describes the release version, publication timestamp, minimum
supported launcher version, release-notes URL, and platform-specific application
image update archives. The current platform key is resolved through
\`Platform.distributionId()\` (for example, \`windows-x64\` or \`macos-aarch64\`).

The JSON contract is defined by [manifest.schema.json](../release/manifest.schema.json).
The release workflow generates it with [generate_manifest.py](../release/generate_manifest.py)
only after all platform build jobs have completed. The generator validates the
completed document against the Draft 2020-12 schema using the pinned dependency
in [requirements.txt](../release/requirements.txt); a schema mismatch blocks publication.

## Artifact validation

For every required platform, manifest generation:

1. Requires the expected versioned ZIP filename.
2. Requires the corresponding SHA-256 sidecar generated by Gradle.
3. Recomputes SHA-256 from the downloaded CI artifact and compares it with the sidecar.
4. Opens every ZIP, verifies its CRCs, rejects traversal paths, symbolic links and encrypted entries, and checks for the platform's native launcher, bundled runtime and application configuration.
5. Rejects extra or untracked files so the published release contains only the validated platform archives, checksum sidecars and manifest.
6. Records the artifact filename, GitHub release URL, byte size and SHA-256 digest.
7. Fails publication if any required platform artifact is missing or invalid.

At update time, Vanta validates the manifest schema version, product, channel,
semantic version, timestamp, minimum launcher version, release-notes URL, and
exact root/artifact field sets. It requires all five supported platform entries
and validates every entry's versioned filename, exact GitHub release URL, size
and SHA-256 format—not only the artifact selected by the current machine. The
updater then verifies both the downloaded byte count and digest before handing
the archive to the transactional installer.

Manifest responses are limited to 1 MiB and must resolve to GitHub's trusted
metadata or release-asset hosts. Artifact downloads retain their existing
redirect-host and maximum-size checks.

## Build provenance

The release workflow creates GitHub artifact attestations for every published
release asset after the manifest has passed schema and package validation.
These attestations bind the artifact digests to the GitHub Actions workflow
identity and its source repository. They provide independently verifiable
build provenance; they do not replace the launcher's own release-manifest
signature verification.

With GitHub CLI installed, verify a downloaded release asset against the
repository's published provenance using:

```sh
gh attestation verify Vanta-1.3.3-windows-x64.zip --repo ItsDropper/Vanta
```

Use the actual downloaded filename in place of the example. The manifest itself
can be verified in the same way. A valid attestation establishes which trusted
workflow produced the artifact, while the still-pending detached Ed25519
manifest signature will provide the launcher's independent publisher-authenticity
check.

## Compatibility and migration

Older published releases do not contain \`manifest.json\`. Until the first
manifest-backed stable release is published, a 404 from the stable manifest
endpoint triggers the legacy GitHub Releases API lookup. Other manifest errors
fail closed; malformed or untrusted manifests do not silently fall back to the
legacy path.

The \`min_launcher_version\` field prevents a release from being installed by a
launcher whose updater is too old to understand its requirements. Raise this
minimum only when a release actually requires a newer launcher.

## Current scope and security boundary

The first manifest schema describes the five platform-specific application
image ZIPs used by the transactional updater: Windows x64, Linux x64/ARM64 and
macOS x64/ARM64. It does not yet describe the small bootstrap installer
(\`VantaSetup.exe\`) or native MSI/DEB/RPM/DMG packages. Those need their own
build and artifact pipeline before they can be advertised accurately.

The manifest is currently retrieved over HTTPS from GitHub. Its embedded
SHA-256 digest detects artifact corruption and mismatches, but **does not
authenticate the manifest publisher independently**: an attacker able to
replace both the manifest and release assets could replace the digest too.
Detached Ed25519 signing and in-launcher public-key verification remain a
separate required hardening step before treating the release metadata as
cryptographically authenticated.
